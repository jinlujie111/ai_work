# 学习目标规划 · 可执行性与资源评估

## 0. 结论先行

| 问题 | 判断 |
|------|------|
| 工程上能不能做出来？ | **能。** P0 闭环技术成熟，1–2 人可在 4–8 周内做出可测 MVP |
| 产品上能不能让人「执行」？ | **不确定，必须验证。** 这是主风险，不是技术风险 |
| 未来走 App 可行吗？ | **可行，且更利于留存**；建议小程序验证闭环后再做 |
| 要不要自建 GPU？ | **不要。** 调国内模型 API；服务器只需普通 CPU 机 |
| 起步机器多大？ | **2 核 4G** 足够种子用户；百人级并发仍偏 I/O，不吃满 CPU |

## 1. 可执行性（分两层）

### 1.1 工程可执行性：高

| 模块 | 难度 | 说明 |
|------|------|------|
| 微信登录 + 基础 CRUD | 低 | 成熟路径 |
| 目标 / 阶段 / 任务数据模型 | 中低 | 表结构清晰，关键是版本表 |
| LangGraph 四条工作流 | 中 | 结构化 JSON + 规则校验即可，勿做成自由 Agent |
| 计划确认 / 重规划 diff | 中 | 产品差异点，但实现是版本对比，非黑科技 |
| 定时日计划 / 周复盘 | 中低 | Celery 或云定时 + 队列 |
| 支付 / 会员 | 中 | 小程序虚拟支付有资质与类目门槛 |
| 订阅消息触达 | 中 | 次数有限，不能当推送主力 |

**不宜高估的部分：** AI「智能」本身——难点在提示词、负载规则、确认交互，不在框架。

**建议砍掉的复杂度（保可执行）：**

- 不做多 Agent 自由协作  
- 不做本地大模型  
- V1 不做日历双向同步  
- 重规划先覆盖「延期 / 超时」两种主因  

### 1.2 产品可执行性：中（主风险）

「可执行」真正卡在用户是否：

1. 愿意建第一个目标  
2. 确认 AI 计划  
3. 连续用 7 天勾选  
4. 至少接受 1 次重规划  

任一环断，产品就退化成「好玩一次的 AI 待办」。

| 风险 | 对可执行性的影响 | 缓解 |
|------|------------------|------|
| 计划太理想 | 确认率低 / 完成率低 | 强约束可用时间；模板化垂直场景 |
| 调整不信任 | 不接受重规划 | 必确认 + diff + 回滚 |
| 小程序无强推送 | 次日留存差 | 订阅消息 + 社群 + 首页「欠账」感 |
| AI 成本失控 | 商业不可持续 | 额度墙；工作流限步数 |

**判断：** 值得做 MVP；是否值得做成 App，取决于上述 4 环的种子数据，而不是架构图。

## 2. 未来走 App：可行，但分阶段

### 2.1 结论

| 项 | 建议 |
|----|------|
| 要不要做 App？ | **要，作为第二阶段载体**，不是 MVP 载体 |
| 何时启动？ | 小程序验证：7 日留存与调整接受率达标后再启 |
| 后端能否复用？ | **几乎全部复用**（FastAPI / 工作流 / PG / Redis） |
| 前端？ | 重做 UI；可用 uni-app / Flutter / 双端原生 |
| 最大收益 | 系统推送、桌面小组件、日历、后台提醒——补小程序触达短板 |
| 最大成本 | 双端包体、审核、苹果 IAP 分成、运营双端 |

### 2.2 为什么 App 对「学习目标规划」更匹配

本产品是**日活学习执行工具**。留存依赖「每天被拉回来」。

| 能力 | 小程序 | App |
|------|--------|-----|
| 安装摩擦 | 极低（微信内） | 较高 |
| 获客 | 微信内分享强 | 应用商店弱、投放贵 |
| 推送 | 订阅消息有限 | 系统推送强 |
| 日历 / 小组件 | 弱 | 强 |
| 语音 / 本地能力 | 受限 | 更完整 |
| 支付 | 微信虚拟支付（资质） | 安卓灵活；iOS 走 IAP |

**策略：** 小程序负责**获客与验证**；App 负责**留存与付费加深**。不要一上来双端全做。

### 2.3 App 路径风险

1. 未验证留存就做 App → 开发量翻倍，结论不变  
2. iOS 审核对「订阅制效率工具」常见，需准备隐私与自动续费说明  
3. 若只做安卓，国内分发渠道成本高；建议后期双端  

### 2.4 技术迁移成本（量级）

| 工作 | 人周（约） |
|------|------------|
| 小程序 MVP（P0） | 4–8 |
| App 壳 + 今日/目标/助手四 Tab（复用 API） | 6–12 |
| 推送 / 小组件 / 日历 | 2–4 |
| 双端支付与会员对齐 | 2–3 |

后端在 App 阶段主要是：鉴权多端、推送 token、少量接口扩展——**不是重写**。

## 3. 内存 / CPU 需求

前提：**大模型走云 API，本机不跑推理。** 服务器是编排层（I/O 等待为主），不是 GPU 机。

### 3.1 客户端（用户手机）

| 形态 | 内存占用（约） | CPU | 说明 |
|------|----------------|-----|------|
| 微信小程序 | 由微信容器管理，业务侧通常 **几十 MB 级** | 低 | 列表 + 表单 + 对话流，无重计算 |
| 未来 App | 常驻 **80–200 MB** 量级（视框架） | 低–中 | 聊天流式、本地缓存；勿在端上跑模型 |

用户侧**不需要**为本产品准备「高配机」；中低端安卓可用。

### 3.2 服务端（你要买的云主机）

按阶段估算（国内云，模型外调）：

| 阶段 | 用户规模（约） | 推荐配置 | 内存 | CPU | 说明 |
|------|----------------|----------|------|-----|------|
| 开发 / 内测 | 1–20 | 2 核 2G–4G | 2–4 GB | 2 vCPU | API + PG + Redis 可同机或拆轻量 |
| 种子验证 | ~100 DAU 低 | **2 核 4G** | **4 GB** | **2 vCPU** | 推荐起步规格 |
| 小规模上线 | 1k 注册 / 百级 DAU | 2 核 4G–8G | 4–8 GB | 2 vCPU | PG/Redis 建议分离或托管 |
| 成长 | 1万注册 / 千级 DAU | API 2–4 核；库托管 | API 4–8 GB | 2–4 vCPU | 水平扩 API；队列扛尖峰 |
| 再往后 | 更高 | 多副本 + 托管 PG/Redis | 按并发加 | 按并发加 | 瓶颈在 LLM QPS 与费用，不在 CPU |

**单进程量级参考（行业惯例，非实测）：**

- FastAPI + LangGraph 单副本：请求 **0.25–1 vCPU**、内存 **512 MB–1 GB** 起可跑  
- 实际同机还要给 PostgreSQL（约 0.5–1.5 GB）、Redis（约 128–512 MB）、系统留白  

故 **2C4G 单机** 对种子期是合理甜点；再抠到 2C2G 也能开发，但 PG + 工作流峰值易紧。

### 3.3 负载特征（决定「要不要加 CPU」）

| 操作 | 频率 | 资源特征 |
|------|------|----------|
| 打开今日、勾选完成 | 高 | 轻 DB，几乎不吃 CPU |
| 创建目标 / 拆解 | 低 | 多次 LLM 调用，**等网络**，本地 CPU 闲 |
| 延期重规划 | 中低 | 同上，I/O 密集 |
| 每日定时生成计划 | 集中在清晨 | 队列削峰；短时并发升高 |
| 每周复盘 | 周一次 | 可错峰 |

**结论：** 扩容优先看「同时有多少人在跑工作流」，不是「总用户数」。用户 1 万但多数只勾选，CPU 仍然很闲；早上 8 点集中重规划，才需要队列 + 多 worker。

### 3.4 不要买的东西

| 项 | 原因 |
|----|------|
| GPU 云主机 | 你不自托管大模型 |
| 起步 8 核 32G | 浪费；钱应花在模型额度与种子运营 |
| 把对话状态只放进程内存 | 一扩副本就丢；状态进 PG/Redis |

### 3.5 成本结构提醒（比 CPU 更重要）

在百人～千人阶段，月成本大致是：

```text
云主机（2C4G）     相对固定、较小
PostgreSQL/Redis   小或含在主机内
大模型 API         随「规划/调整/复盘次数」线性涨 ← 主成本
```

所以资源规划要盯 **单用户 AI 调用次数与 token**，不是只盯机器配置。PRD 里的额度墙是生存条件。

## 4. 建议落地顺序

1. **现在：** 2C4G + 小程序 P0，验证四环闭环  
2. **指标过线后：** 补会员与额度；考虑安卓 App（推送优先）  
3. **留存稳定后：** iOS + 小组件/日历  
4. **全程：** 模型外调，编排层按并发水平扩展
